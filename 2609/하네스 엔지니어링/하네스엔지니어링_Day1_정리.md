## 1. 핵심 개념

### 1-1. 생성형 AI = 랜덤/분포, 하네스 엔지니어링 = 분산 줄이기
- 생성형(Generative) AI가 창의적인 이유는 본질적으로 **랜덤**이기 때문. 같은 요청도 매번 다른 결과가 나옴.
- 모델 성능은 "평균"의 개념이고, 실제 결과는 평균 주위로 **분포(표준편차)**를 가짐. 벤치마크 점수도 절댓값이 아니라 평균.
- **하네스 엔지니어링의 본질 = 이 분포(편차)를 좁히는 작업.** 모델 성능 자체를 뛰어넘는 게 아니라, 흩어진 결과물을 원하는 좁은 범위로 수렴시키는 것.
- "모델이 좋아지면 하네스가 필요 없다"는 주장(하네스 무용론)에 대해: 모델이 좋아질수록 필요한 하네스의 양은 줄어들지만(과거 20 → 지금 10 수준), 완전히 없어지긴 어렵다고 봄. 특히 **회사 내부처럼 외부 지식과 다른 방식으로 움직이는 도메인**에서는 여전히 필요.

### 1-2. 멀티에이전트 = "한 명이 가면(페르소나)을 바꿔가며 연기하는 것"
- 멀티에이전트라고 해서 실제로 다른 AI들이 여러 개 있는 게 아님. **자아(모델)는 하나**이고, 상황에 맞는 지식/역할만 활성화(마스크)해서 쓰는 구조.
- 전체 지식을 한 번에 다 활성화하면 서버가 못 버티기 때문에, 필요한 지식만 그때그때 끌어옴 → 이게 전문성처럼 보이는 이유.
- 마스크(에이전트)마다 **스킬**을 붙여주면 해당 업무에 능동적으로/빠르게 대응. 각 에이전트를 **서브에이전트**로 만들면 동시 작업(병렬)도 가능.

### 1-3. 단일 에이전트 vs 멀티 에이전트
| 구분 | 단일 에이전트 | 멀티 에이전트 |
|---|---|---|
| 특징 | 제너럴리스트, 마스크가 넓음 | 마스크가 좁고 전문성 있음, 스킬 결합 |
| 장점 | 단순, 토큰 적게 씀 | 전문 영역 빠르게 처리, 서브에이전트로 병렬 처리 가능 |
| 단점 | 전문성 낮음, 동시작업 불가, 품질 편차 | 토큰 소모 큼, PC 로컬 성능 요구, 설계(오케스트레이션)가 어려움 |
| 오해 주의 | — | "에이전트가 여러 개면 지식이 더 많다"는 착각 금지 — 같은 모델 위에서 동작하므로 지식 총량은 동일. 다만 병렬 처리·전문화·모델 티어링에서 이득 |

### 1-4. 컨텍스트 윈도우
- AI가 "한 번에 기억할 수 있는 총량". 다 차면 오래된 내용부터 축약(압축)하면서 최근 내용 위주로 유지 → 세션이 길어질수록 기억력이 점점 떨어짐. 그래서 "새 세션에서 시작하라"는 권장이 나옴.
- 과거엔 창이 작아서(2만 토큰대) 문서를 짧게 써야 했지만, 지금은 100만 토큰급(Sonnet 포함)으로 커져서 상대적으로 여유가 생김.
- `agent.md` 파일은 항상 로드되는 값이라 커질수록 컨텍스트를 잡아먹음 → 되도록 짧게 쓰고 세부 내용은 다른 파일에 **링크**로 연결하는 방식을 권장 (강사님 본인은 길게 쓰는 스타일이라고 인정).

## 2. 하네스 구조/파일 체계

### 2-1. 표준 폴더 구조 (템플릿 공통)
```
프로젝트/
├── agents/     # 에이전트 정의 파일들 (.md)
├── skills/     # 스킬 폴더 (폴더명 = 스킬명, 안에 SKILL.md + 스크립트)
├── scripts/    # 스크립트 (TypeScript/Bun 등)
├── docs/       # 각종 문서 (phase-definition 등)
├── memory/     # 회의결과·변경이력 로그
├── AGENTS.md   # 모든 AI 툴이 공통으로 가장 먼저 읽는 표준 파일 (업계 표준, 약 2년 전 규격)
├── CLAUDE.md   # 클로드 전용 오버라이드
├── GEMINI.md   # Gemini 전용 오버라이드 (코덱스는 별도 파일 없이 AGENTS.md만 봄)
└── .env / .env.sample  # 외부 API 키 등 환경변수
```

### 2-2. `AGENTS.md`의 위상
- **모든 AI 툴(클로드, Gemini, 코덱스, 커서 등)이 작업 폴더에서 가장 먼저 찾는 파일.** 특정 벤더 규칙이 아니라 업계 표준.
- 이 파일에 전체 에이전트 로스터를 요약하고, 상세 내용은 각 `agents/*.md`로 링크 → 컨텍스트 절약.
- 하나의 하네스를 만들어도 특정 벤더에 종속되지 않도록(HA 관점) `AGENTS.md` 표준을 지키면 Claude가 죽어도 Gemini/코덱스로 대체 가능 (최근 Gemini+Claude 동시 장애 사례 언급).

### 2-3. 에이전트 vs 스킬 vs 스크립트 — 역할 차이
- **에이전트(.md)**: 판단 주체. "마스크"이자 시스템 프롬프트. 상태(맥락)를 들고 다니는 존재.
- **스킬(폴더+SKILL.md+스크립트)**: AI가 상황에 맞게 **스스로 골라 쓰는** 도구. MCP와 달리 사람이 트리거하지 않고 AI가 알아서 탐지해서 사용.
- **스크립트**: 결정적(deterministic) 로직. 상태(state)가 없음 — 상태는 항상 위의 에이전트가 들고 있음.
- 흐름: PM(오케스트레이터) → 적합한 에이전트 호출(핸드오프) → 에이전트가 필요한 스킬 탐색 → 스킬이 스크립트 실행 → **불확정적인 에이전트 판단을 확정적인 스크립트 산출물로 변환**하는 구조.
- 밸리데이션(검증) 스크립트가 많은 이유: 생성형 AI는 95% 맞아도 5%는 이상하게 나올 수 있음 → 값싼 모델을 쓸수록 안전장치(검증 스크립트)를 더 촘촘히 걸어야 함. 반대로 최상위 모델(Opus 등)만 무제한으로 쓸 수 있다면 이런 장치가 덜 필요.

### 2-4. 오케스트레이션 (PM 구조)
- 강사님 설계: **PM 에이전트가 싱글 포인트 오브 엔트리** — 직접 실행하지 않고 코디네이터 역할만 함. 다른 스페셜리스트 에이전트로 직접 명령이 안 가게 강제 설계(`PM only invocation` 규칙).
- 실행 시 "PM 에이전트"라고 **명시적으로 불러야** 오케스트레이션 트리거가 확실히 동작. 그냥 대화하듯 시키면 랜덤하게 PM이 잡히거나 안 잡힐 수 있음.
- 이 구조는 강사님의 설계 선택일 뿐 "정답"은 아님 — 개발/디자인/DBA 등으로 나눠 다른 구조로 설계 가능.

### 2-5. 모델 티어링
- 에이전트별로 어떤 모델(Opus/Sonnet/Haiku, Gemini 모델 등)을 쓸지 미리 지정해둠 → 중요도 낮은 작업엔 싼 모델, 품질이 중요한 작업엔 비싼 모델 지정 → 토큰 비용 절감.
- 계획(Plan) 단계는 가급적 상위 티어(Opus) 권장, 코딩은 의외로 중간~하위 티어로도 충분한 경우가 많음. 검수(QA)는 반드시 중간 티어 이상 권장(검증 확산 방지).
- AI가 스스로 적절한 모델을 추천해서 배정하기도 함(예: 한국어 전문 에이전트에 Opus를 자동 지정).

### 2-6. 디스패치(순차 vs 병렬)
- 순차: 쉬움 — 산출물이 그대로 다음 단계로 핸드오프.
- 병렬: 어려움 — 작업 A/B/C를 동시에 줘도 완료 시간이 다 다르면(1시간/30분/3시간) 가장 느린 작업이 전체를 지연시킴 → **작업 분할 설계(트래픽 밸런싱) 감각**이 필요. 처음부터 잘 안 되고 여러 번 튜닝해서 얻는 경험치의 영역.

## 3. 오늘 진행한 실습

### 3-1. `co-consult` 템플릿 — K-뷰티 시장조사
- `ai-workspace-standards` 저장소의 템플릿 중 `co-consult`로 신규 프로젝트("컨설팅") 스캐폴딩.
- 흐름: PM 배정 → 리서치 스페셜리스트가 계획 수립 → **사용자 승인(Human-in-the-loop)** → 실행 핸드오프 → 최종 QA → 동기화.
- 서브에이전트가 자율적으로 적합한 모델(예: Opus)을 선택해 리서치 수행. 시장 규모/트렌드 보고서가 약 10분 만에 산출(과거 2~3일 걸리던 작업).
- 결과물은 `deliverables/` 폴더에 리포트 파일(K-Beauty, K-Food)로 저장됨.

### 3-2. `co-develop` 템플릿 — 홍보 웹사이트 빌드
- `co-develop` 기본 로스터: PM, Architect, Designer, Code Writer, Security Monitor, Test Runner (단순 워터폴형 6단계 파이프라인).
- 컨설팅 산출물(K-Beauty/K-Food 리포트) 2개만 던져서 "활용 홍보 사이트를 만들겠다"고 지시 → 별도 PRD 없이 AI가 멀티페이지 여부 등을 스스로 물어보며 설계.
- **부족한 전문성은 그때그때 에이전트를 추가**: 기본 로스터엔 '홍보 전문가', '한국학 전문가'가 없었음 → AI에게 직접 "뭐가 부족한 것 같아?"라고 열린 질문을 던져 스스로 판단하게 하고, 필요한 에이전트를 추가 생성.
- 새 에이전트 추가 후 **회의 스킬**로 에이전트들끼리 토론시켜 디자인 고도화 방안 도출 → 실제로 의미 있는 관점(홍보/한국학)이 반영된 피드백이 나옴.
- 디자인 취향(컬러/톤)은 하네스로 자동화하기 어려운 영역 — 취향을 아예 MD 파일로 명문화해두거나, 벤치마킹할 사이트를 알려주는 방식으로 보완.
- DB 관련 스킬이 필요할 때, AI에게 "DBA 에이전트를 새로 만드는 게 나을지" 물어봄 → AI가 "새 에이전트 대신 기존 Architect에 스킬만 추가하자"고 제안 → 실제로 그렇게 진행 (에이전트를 늘리는 것보다 기존 역할에 스킬을 붙이는 게 나은 경우가 있음을 보여준 사례).

### 3-3. `co-deck` 템플릿 — 발표자료(슬라이드) 생성
- 코덱(co-deck) 에이전트 팀 특징: 검색(리서치) → 교차검증(소스 베리피케이션) → 스토리텔링(기승전결 서사 구조) → 요청한 분량(예: 20페이지/30분)에 맞춰 확장/압축.
- NotebookLM과 차별점: NotebookLM은 고정 길이만 생성 가능하지만, 이 하네스는 원하는 페이지 수/시간에 맞춰 자유롭게 조절.
- HTML로 산출물 생성 → 필요시 PDF/PPT로 변환. `docs/themes/preview.html`에서 스타일 프리셋(예: Peach Enhanced × Premium Dark) 미리보기 확인 후 지정.
- 실습 예시: 컨설팅 산출물을 활용해 "한식 세계화" 발표자료, 대상=실무진, 20페이지, 테마=Peach Enhanced, 스타일=Premium Dark, 관련 이미지 자동 다운로드 지정.

### 3-4. 한국 공공데이터 API 스킬 연동 (`co-export` 템플릿)
- `co-export`(수출입 특화) 템플릿에 "한국 특화(Korea-specific)" 옵션을 선택하면 3종 스킬이 자동으로 붙음:
  1. **DART(전자공시)** — 기업 재무공시 데이터, 키 발급 절차 간단(메일 대신 임의 키값 가능)
  2. **국가법령정보센터** — 법령 조회, 키 발급 간단
  3. **공공데이터포털(data.go.kr) / KOSIS(국가통계포털)** — 이 둘은 **키 발급 체계가 서로 다름**(주의: 강사님도 라이브에서 헷갈렸던 부분)
     - KOSIS: 별도 API 키 발급
     - 공공데이터포털: 키 발급 + **활용하려는 데이터셋마다 별도 "활용신청" 승인** 필요 (승인 후 2년 유효)
     - 관세청 수출입 데이터는 KOSIS와 data.go.kr(무역통계) 양쪽에 중복 존재
- `.env.sample`을 `.env`로 복사해 발급받은 키를 채우는 방식. 외부 데이터라 유출 리스크는 낮은 편이지만, 노출 시 폐기 후 재발급 원칙은 동일 적용.
- 커뮤니티 저장소 **"K-Skill"**(GitHub) — 철도/고속버스 예매, 여행정보, 부동산 실거래가, 사업자등록 조회 등 한국 특화 스킬 모음. 그대로 신뢰하지 말고 참고해서 직접 만드는 것도 방법.

## 4. 커리어/조직 관점 인사이트

- **개발자가 갈 수 있는 3가지 방향**: ① 아키텍트(설계) ② 리뷰어/PM(산출물 품질 책임자, 의사결정자) ③ 코디네이터(현업-기술 연결). 순수 코딩만 하는 영역은 축소.
- **매니저 책임의 변화**: 과거엔 팀원에게 일을 시키고 검토→위로 보고하며 책임이 분산됐지만, 이제는 AI에게 시킨 결과에 대한 책임을 본인이 직접 져야 함. "이름만 매니저였는데 이제 진짜 매니저가 된다."
- **1인 다중 프로젝트 시대**: 한 사람이 동시에 2~3개 프로젝트를 진행하는 게 가능해짐 → 그만큼 일이 줄어드는 게 아니라 **관리해야 할 화면(모니터)과 의사결정이 늘어남**.
- **IT-현업 경계 붕괴**: 비개발 현업 부서가 AI로 직접 간단한 웹사이트/툴을 만들 수 있게 되면서, 개발자의 역할은 "도구(하네스) 자체를 현업이 쓰기 좋게 만들어주는 것"으로 이동 (낫을 만들어주던 사람 → 가위/집게 등 다양한 도구를 만들 수 있는 틀을 만들어주는 사람).
- **문서화 패러다임 변화**: Word/PPT 산출물은 만든 뒤 다시 손대지 않아 금방 낡음(문서 부채). HTML/MD 기반 문서는 코드가 바뀔 때마다 AI가 함께 갱신해줄 수 있어 "살아있는 문서"가 됨. 위키(예: Confluence 등)에 MD를 레거시로 붙이는 방식 추천.
- **검수 관점**: 수십~수백 페이지 문서/수십만 줄 코드를 사람이 다 검토하는 건 불가능했지만, AI에게 검수를 맡기면 구조적 문제(설계 이탈, 누락)를 걸러낼 수 있어 품질 관리 방식 자체가 바뀜.
- **1년 사이 실무 방식 변화**: 작년까지는 "PRD 작성 → 스펙 분석 → 코딩 도구에 던지기" 순서가 정석이었지만, 지금은 원본 자료만 던져도 AI가 스스로 계획을 세우고 되물어보는 방식으로 충분한 경우가 많아짐(1년 전 방식은 이미 구식).
- **중소기업 AI 도입 속도**: 직원 48명 → 7명으로 줄이고도 AI 자동화 루프(미니 슬랙+AI+피그마 MCP)로 서비스를 계속 고도화하는 실제 사례 언급 — 대기업보다 중소기업의 실질적 도입 속도가 더 빠를 수 있다는 인사이트.

## 5. 실전 팁 모음

- **이미지 관련 작업은 토큰을 크게 잡아먹음** (다운로드한 이미지가 적합한지 검토·재다운로드를 반복하기 때문) — 저렴한 모델 티어로 처리하는 걸 권장.
- **`memory/` 폴더**: 회의 결과, 변경 이력을 자동 기록 → "너 뭐 바꿨어?"라고 물으면 이 로그를 참조해서 답변.
- **세션 한도 도달 시 자동 재개 옵션**: 한도 도달 시 작업을 큐에 걸어두면, 한도가 초기화된 후 자동으로 이어서 실행 — 급하지 않은 작업을 미리 걸어두는 용도로 유용.
- **모바일 연동**: 데스크탑에서 만든 프로젝트 폴더를 클로드 앱의 "Cowork(코옥)" 메뉴에서 폴더로 추가하면, 휴대폰에서도 같은 세션에 명령을 내릴 수 있음 (단, PC가 켜져 있어야 함). 태블릿이 화면 크기상 더 편함.
- **야간 배치**: 5시간 세션 한도를 밤 시간에 맞춰 걸어두면(예: 밤 10시~새벽3시) 자는 동안 작업 진행 가능. 단, 회사 PC를 그렇게 켜두는 건 보안상 지양.
- **보안/데이터 거버넌스**: "외부 유출 안 되지만 못 쓰는 툴 vs 유출 리스크는 있지만 활용도 높은 툴" 사이의 트레이드오프이며 정답은 없음 — 조직 내 정보보안팀과 논의가 필요한 영역. Enterprise/Team 플랜은 계약상 학습 미반영을 명시하는 경우가 많아 상대적으로 안전.
- **레드팀/블루팀 스킬(`co-security`)**: 가상 공격/방어 훈련 가능하지만 **운영 중인 실제 사이트에는 절대 사용 금지** — 개발 환경에서만 점검용으로 활용.
- **PM 직접 호출 습관화**: "PM 에이전트"라고 명시하지 않으면 라우팅이 랜덤해질 수 있음 — 하네스를 만들어놓고 왜 안 돌아가나 싶을 땐 호출 방식부터 점검.
- **번역/한국어 사용 지양**: 문서 대부분을 영어로 작성하는 이유 — 한글은 토큰을 더 많이 소비(약 1.7배 수준 언급)하기 때문. 프로젝트 문서량이 많아질수록 영향이 커짐.
